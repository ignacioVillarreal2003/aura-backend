Plan #1 (revisado) — Surfacing del contexto en la tubería compartida

Dónde vive realmente el formateo (document_question)

DocumentQuestionService (extends StreamingGenerationService)
→ ContextRetrievalProcessor.run()   → state.fragments  (FragmentResponse con summary + document.description)
→ [opcional] ContextReductionProcessor → state.reduced_context
→ base_generation_service._build_llm_messages()
→ build_context_block(state, max_context_chars, attached_reserve_ratio)   ← AQUÍ
→ build_generation_messages(... context_block ...)

build_context_block() (en generation_messages.py) hoy:

- Si hay reduced_context → devuelve solo eso (síntesis multi-pasada).
- Si no → renderiza attached_fragments (prioritario) + rag_only_fragments (complementario) vía _render_fragments(), que
  produce [FRAGMENTO i — nombre_doc · pág. X]\ncontent.

Diferencia clave vs. el rag_agent: acá los fragmentos son una lista plana, no agrupada por documento. Así que la
description no se puede poner como cabecera por documento sin
repetirla. La solución limpia es un preámbulo único con las descripciones de los documentos involucrados, una sola vez.

Bonus: como el cambio es en la tubería compartida, lo heredan automáticamente document_question y todos los servicios
que extienden StreamingGenerationService/structured
(general_chat, decision_brief, etc.). Por eso los defaults van conservadores.

Cambios concretos en generation_messages.py

a) Preámbulo de descripciones (nuevo, una vez por bloque):
=== DOCUMENTOS EN CONTEXTO ===
#12 — Reglamento X: <description recortada a max_description_chars>
#27 — Resolución Y: <description recortada>

- Se construye desde los documentos únicos de state.all_fragments (cada FragmentResponse.document trae id, name,
  description).
- Se inserta al inicio de build_context_block(), también en la rama reduced_context (la reducción descarta la identidad
  de los documentos, así que el preámbulo la reincorpora).
- Solo lista documentos que tienen description (si ninguno tiene, no se agrega el bloque → comportamiento actual
  intacto).

b) Resumen por fragmento en _render_fragments():
[FRAGMENTO 1 — Reglamento X · pág. 3]
[Resumen]: <fragment.summary recortado a max_summary_chars>
<content>

- Gated por flag; off por default.

c) Presupuesto (crítico, porque comparten max_context_chars):

- El preámbulo se mide y se descuenta del budget total antes de repartir entre attached/rag (hoy el reparto usa
  attached_reserve_ratio). Orden: budget_restante =
  max_context_chars − len(preámbulo).
- Topes propios max_description_chars y max_summary_chars para que ni una descripción larga ni un summary se coman el
  contexto de los fragmentos.
- El summary también cuenta dentro del budget que ya respeta _render_fragments().

Settings nuevos (en GenerationSettings, defaults conservadores)

- include_document_descriptions: bool = True
- include_fragment_summary: bool = False
- max_description_chars: int = 500
- max_summary_chars: int = 300
- max_descriptions_block_chars: int = 1_500 (tope del preámbulo completo, anti-explosión si hay muchos documentos)

Plumbing: DocumentQuestionServiceSettings.to_generation_settings() los reenvía (hoy solo pasa history_messages_window,
max_context_chars, max_context_tokens).

Riesgos / decisiones

- Rama reduced_context: decisión recomendada → preámbulo de descripciones sí se mantiene (barato y reincorpora identidad
  perdida). Alternativa más cara: meter las descripciones
  en el input de la reducción (_fragment_units, que hoy usa solo [nombre] content) — lo dejo fuera de scope salvo que lo
  pidas.
- Doble fuente / citas: el summary podría ser citado como si fuera el original → etiquetado [Resumen] + off por default.
  Las citas [Documento #ID]/[FRAGMENTO i] no cambian.
- Documentos sin description (enrichment pendiente/fallado): se omiten del preámbulo; degradación elegante.
- Alcance compartido: al tocar generation_messages.py/GenerationSettings, el cambio impacta a todos los servicios de la
  familia. Es deseable, pero los defaults conservadores
  evitan sorpresas; cada servicio puede sobreescribir vía su to_generation_settings().
- Sin migraciones de BD, sin tocar aura-document-processing-service. Todo el dato (summary, document.description) ya
  viaja en el FragmentResponse.
- rag_agent queda fuera de scope: tiene su propio context_formatting.py. Si querés, en un paso aparte espejo el mismo
  cambio ahí, pero como no es tu flujo principal lo dejo
  intacto.

Esfuerzo

Bajo (~1 archivo de lógica + 2 de settings/plumbing + tests). Cero riesgo de datos.
